# PC 存储空间管理策略（通用版）

> 目标：让磁盘空间**可解释、可预算、可清理、可迁移、可审计**，避免“空间莫名其妙没了”和“文件夹越建越乱”。
>
> 这份策略既适用于个人电脑，也适用于代码仓库/项目工作区。`pc-manager` 的 `audit`、AI 建议和 `storage-strategy` skill 都以本文为规则来源。

## 1. 核心原则

1. **分层存放**：系统、应用、活跃项目、媒体、归档、备份分开，不混在同一个盘或同一个根目录。
2. **先预算后使用**：每个盘保留最低空闲空间；大目录增长要有上限。
3. **可再生数据可删，用户数据只移不删**：缓存、构建产物、日志可以清理；照片、文档、聊天记录、数据库只能归档/迁移。
4. **一个类别一个权威根目录**：`Media`、`Work`、`Archive`、`Downloads` 各只有一个主根，避免同名目录散落多盘。
5. **热/温/冷分层**：最近 30 天为热数据；30–365 天为温数据；超过 1 年或很少访问的进入归档。
6. **先预览再执行**：任何移动/删除都要先生成计划、展示数量和样例、写 manifest。
7. **路径可读**：目录名表达用途；避免 `新建文件夹`、`Copy of`、`final_final`、`_old` 长期存在。
8. **不重复计数**：junction/符号链接、云占位、WinSxS 硬链接不能按普通文件重复计算。

## 2. 容量预算模型

### 2.1 空闲空间红线

| 盘类型 | 建议最低空闲 | 警戒线 | 处理 |
|---|---:|---:|---|
| 系统盘（C:） | ≥ 15% 或 50 GB | < 10% 或 30 GB | 立即清理/迁移 |
| 数据盘 | ≥ 10% 或 20 GB | < 5% 或 20 GB | 归档/迁移/扩容 |
| 备份盘 | ≥ 20% | < 10% | 停止新增备份，清理旧代 |

系统盘低于 5% 会导致 Windows 更新、页面文件、临时文件和应用缓存异常，应视为 P0。

### 2.2 分层模型

| 层级 | 内容 | 推荐位置 | 特点 |
|---|---|---|---|
| Tier 0 | Windows、驱动、常驻应用 | C: | 不随意移动，保留足够空闲 |
| Tier 1 | 活跃项目、当前工作区、开发环境 | 最快的 SSD（通常是 D: 或 E:） | 高频读写，可重建缓存 |
| Tier 2 | 照片、视频、文档、素材 | 大容量数据盘 | 体量大，按年月/项目归档 |
| Tier 3 | 归档、备份、旧版本、冷数据 | 第二数据盘/外置盘/云 | 低频访问，必须可检索 |

### 2.3 类别预算（建议上限）

| 类别 | 占已用空间建议 | 说明 |
|---|---:|---|
| 操作系统 + 应用 | ≤ 35%（系统盘） | 超出时检查应用/游戏/缓存 |
| 活跃项目/工作区 | ≤ 25%（数据盘） | 构建产物、依赖缓存不应长期留在仓库 |
| 媒体 | ≤ 45%（数据盘） | 按 `YYYY\YYYY-MM` 归档 |
| 下载/临时 | ≤ 5% | 7 天/30 天分流 |
| 归档/备份 | ≤ 20% | 保留代次，不无限增长 |
| 空闲 | ≥ 10–15% | 不低于红线 |

这些是通用预算，不是硬性配额；`audit` 会按实际盘容量和使用率给出偏差。

## 3. 目录规范

### 3.1 推荐的机器级目录

```text
C:\
  Program Files\            # 系统级应用（安装器决定，不手动搬）
  Program Files (x86)\
  Users\<user>\
    Documents\              # 小体量个人文档
    Downloads\              # 只做收件箱，定期分流
    AppData\                # 应用数据，不手动整体搬

D:\
  Work\                     # 唯一项目工作区根
    <org>\<repo>\
  Media\
    Photos\YYYY\YYYY-MM\
    Videos\YYYY\YYYY-MM\
    Audio\
  Games\                    # Steam/Epic/Xbox 库
  Tools\                    # 便携工具、SDK
  VMs\                      # 虚拟机镜像
  Archive\YYYY\             # 冷数据
  Backup\YYYY-MM\           # 本机备份/快照

E:\
  Media\                    # 第二媒体库（按年月）
  Archive\                  # 长期归档
  Backup\                   # 备份副本
```

> 盘符可以不同。关键是**一台机器只保留一个 Work 根、一个 Media 根、一个 Archive 根、一个 Download 收件箱**。

### 3.2 命名规则

- 项目：`<org>-<repo>` 或直接仓库名，避免空格和中文路径给 CLI 工具带来转义问题。
- 媒体：`YYYY\YYYY-MM_事件或地点\`，保留原始文件名。
- 归档：`YYYY\项目或类别\`，压缩包保留校验和。
- 临时：统一放 `_inbox`、`_tmp`，并在 7 天内清空。
- 禁止长期保留：`新建文件夹`、`New folder`、`Copy of`、`(1)`、`final`、`final_final`、`_old`、`backup`（作为唯一目录名时）。

## 4. 文件生命周期

| 类型 | 热 | 温 | 冷/处理 |
|---|---|---|---|
| 下载文件 | 0–7 天 | 7–30 天 | 30 天后归档或删除 |
| 安装包 | 安装后 30 天 | 30–90 天 | 只保留需要回滚的版本 |
| 缓存/临时 | 随时可清 | — | 可再生，按安全等级清理 |
| 日志/崩溃转储 | 14 天 | 30 天 | 定期清理 |
| 截图/录屏 | 7 天 | 30 天 | 归入媒体或删除 |
| 项目构建产物 | 随时可清 | — | `node_modules`、`target`、`dist`、`build`、`.next`、`__pycache__` |
| 照片/视频 | 当前项目 | 1 年内 | 超过 1 年进入 Archive |
| 文档/资料 | 当前项目 | 1 年内 | 按主题/年份归档 |
| 备份 | 最近 3 代 | 3–6 个月 | 更老代次按保留策略删除 |

## 5. 代码仓库 / 项目空间策略

这是“仓库级”空间管理的重点：

1. **仓库只放源码和必要资源**。
   - 不提交：数据集、模型权重、构建产物、依赖目录、日志、临时导出、虚拟机镜像。
   - `.gitignore` 必须覆盖 `node_modules/`、`.venv/`、`dist/`、`build/`、`target/`、`.next/`、`__pycache__/`、`*.log`、`*.tmp`。
2. **大文件用外部存储**。
   - 图片/视频素材、模型、数据集放 `D:\Data` 或对象存储。
   - 必须版本化的大文件使用 Git LFS，并设置 LFS 预算。
3. **一个工作区根**。
   - 推荐 `D:\Work\<org>\<repo>`；避免同时存在 `D:\GitHub`、`E:\Project`、`C:\Users\<user>\Documents\GitHub` 三套。
4. **仓库体积阈值**。
   - 仓库 > 2 GB：检查 `node_modules`、构建产物、历史大文件。
   - 仓库 > 5 GB：必须拆分数据集/模型，或迁移到数据盘。
   - 仓库 > 20 GB：视为异常，先审计再继续开发。
5. **并行开发用 worktree**，不要复制完整仓库到多个目录。
6. **归档不活跃仓库**。
   - 6 个月未提交的仓库移到 `Archive\repos\` 或打包为 bundle。
   - 保留 remote 作为权威副本，本地只留活跃仓库。
7. **依赖缓存集中管理**。
   - npm/pnpm/yarn/pip/uv/cargo 缓存放默认位置或统一缓存盘；定期清理。
   - 不要把缓存目录提交到仓库或纳入备份。

## 6. 路径与文件夹卫生检查

`audit` 会检查以下常见问题：

- 项目工作区分散在多个盘/多个根目录。
- 下载目录分散或多个大下载根。
- 媒体目录分散，或没有按 `YYYY/YYYY-MM` 组织。
- 顶层大目录使用临时/重复命名。
- 空目录数量异常多（> 5000）。
- junction/符号链接数量异常多（> 200），导致重复计数或备份递归。
- 大文件长期未复核（>= 500 MB，累计 > 20 GB 或数量 > 50）。
- 云占位逻辑大小与本地占用差距过大。
- 应用安装/孤立卸载记录/失效启动项。

### 路径长度与深度

- 目标路径长度 < 200 字符，目录深度 ≤ 8 层。
- 避免 `a\a\a`、`project\project`、`repo\repo` 这类重复嵌套。
- 避免在 OneDrive 同步目录内放 Git 仓库、虚拟机、数据库和大型构建产物。

## 7. 云盘 / 同步目录

- OneDrive/iCloud 的“逻辑大小”不等于本地占用，不要把占位文件当大文件删除或迁移。
- 不要把活跃 Git 仓库、WSL/Docker 镜像、数据库、虚拟机放在同步目录。
- 同步目录只放需要跨设备的小体量文档和最终素材。
- 需要离线的大文件使用“始终保留在此设备”前先确认本地空间预算。
- 定期检查同步冲突文件：`*-副本`、`* (1)`、`*conflict*`。

## 8. 应用、游戏与开发环境

| 类型 | 策略 |
|---|---|
| Steam/Epic/Xbox 游戏 | 安装到 `D:\Games`；不活跃游戏可卸载重下 |
| 虚拟机 | `D:\VMs`；快照定期合并/删除 |
| WSL/Docker | 镜像放数据盘；`docker system prune` 定期清理 |
| Anaconda/Miniconda | 放数据盘；环境按项目创建，删除不用的 env |
| CUDA/SDK/Visual Studio | 可重装到数据盘；保留一个主版本 |
| 浏览器/聊天工具 | 缓存可清；聊天记录/附件单独备份 |
| 便携工具 | `D:\Tools`；不要在每个项目复制一份 |

## 9. 清理、归档、迁移流程

```text
扫描 scan
  → 审计 audit
  → 分类（可清理 / 可迁移 / 需归档 / 需人工复核）
  → 预览（数量、大小、样例、目标路径）
  → 用户确认
  → 执行（带 manifest）
  → 校验空闲空间
  → 重新扫描
```

### 安全等级

| 等级 | 含义 | 动作 |
|---|---|---|
| safe | 可再生缓存/临时文件 | 可直接清理 |
| elevated | 系统缓存/日志 | 需要管理员 |
| confirm | 回收站、旧安装包、孤立数据 | 必须逐项确认 |
| review | 注册表/不明确残留 | 只报告，不自动删除 |

### 删除前检查

- 是否在 `WinSxS`、`Windows\Installer`、`Package Cache`、`System Volume Information`、`Recovery`、pagefile/hiberfil？
- 是否是云占位文件？
- 是否是 junction 目标或备份源？
- 是否有程序正在使用？
- 是否可通过官方卸载器/设置迁移？

## 10. 监控指标与健康评分

`pc-manager audit` 输出健康分 0–100：

| 维度 | 权重（建议） | 说明 |
|---|---:|---|
| 空闲空间 | 25 | 系统盘/数据盘红线 |
| 可清理数据 | 15 | 缓存、安装包、回收站 |
| 路径卫生 | 20 | 工作区/下载/媒体分散、临时命名 |
| 媒体组织 | 15 | 是否按年月归档 |
| 大文件/应用 | 15 | 大文件、应用占用 |
| 云/备份/孤立项 | 10 | 占位、孤立记录、备份 |

评分仅供趋势参考，不替代人工判断。P0/P1/P2 分级：

- **P0**：立即处理，可能影响系统稳定。
- **P1**：本周期处理，空间/路径问题明显。
- **P2**：计划处理，属于整理和优化。

## 11. 决策表（阈值速查）

| 条件 | 级别 | 建议动作 |
|---|---|---|
| 系统盘空闲 < 5% 或 < 20 GB | P0 | 立即清理/迁移，暂停大文件写入 |
| 系统盘空闲 < 15% 或 < 50 GB | P1 | 制定清理/迁移计划 |
| 数据盘空闲 < 10% | P1 | 归档/迁移/扩容 |
| 可清理数据 > 3% 已用且 > 2 GB | P1 | 预览清理 safe，复核 confirm |
| 旧安装包 > 1 GB | P2 | 30 天后删除或归档 |
| 媒体 > 20 GB 且无年月目录 | P2 | 按年月归档 |
| 媒体在系统盘 > 5 GB | P1 | 迁到数据盘 |
| 工作区根 > 1 个 | P2 | 合并到一个 Work 根 |
| 单个工作区 > 5 GB | P2 | 拆数据集/构建产物/Git LFS |
| 下载根 > 5 GB | P2 | 7/30 天分流 |
| 空目录 > 5000 | P2 | 清理确认后删除 |
| junction > 200 | P2 | 记录并避免重复备份 |
| 云占位差距 > 10 GB | P2 | 保持占位，不搬迁 |
| 孤立记录 > 5 | P2 | 诊断页复核 |

## 12. 在 pc-manager 中落地

### 命令

```powershell
# 扫描（只读）
pwsh -File pc-manager.ps1 scan -Drives C,D,E

# 审计（读取扫描，输出健康分、容量预算、路径问题、建议）
pwsh -File pc-manager.ps1 audit -ScanPath reports\scan-<timestamp>.json

# 输出 JSON 给 agent
pwsh -File pc-manager.ps1 audit -ScanPath reports\scan-<timestamp>.json -Json
```

`scan` 会自动把 `Audit` 写入 JSON；旧扫描可用 `audit` 现场计算。

### 与 skill / AI 的关系

- `skills/storage-strategy/SKILL.md` 指导 agent 先读本策略，再跑 `audit`，最后给出 P0/P1/P2 建议。
- GUI 的 `AI 建议` tab 会读取 `Audit.Findings`，生成可编辑、可复制的空间策略建议。
- AI 建议固定按三类输出，顺序和归属如下：
  1. **媒体文件建议**：照片、视频、素材、媒体压缩包；对应 `photo-organizer`。
  2. **工程文件建议**：项目工作区、代码仓库、构建产物、依赖、开发工具/应用迁移；对应 `storage-strategy`、`app-migration`。
  3. **缓存管理文件建议**：缓存、临时文件、日志、旧安装包、回收站、更新残留；对应 `disk-cleanup`。
- 任何移动/清理仍需要预览、确认和 manifest，不能因为“AI 建议”而跳过安全流程。

## 13. 执行节奏

- **每周**：清理下载收件箱、临时文件、截图；检查系统盘空闲。
- **每月**：运行 `scan` + `audit`；处理 P1；归档冷媒体/旧项目；复核大文件。
- **每季度**：整理工作区根；清理旧依赖缓存；检查备份可恢复性；评估是否需要扩容/迁移。
- **每半年**：审计不活跃仓库；归档一年以上媒体；检查云同步冲突和占位策略。
